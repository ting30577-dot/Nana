# Nana 首个纵向切片执行清单

## 1. 目标

不用先实现完整 Nana，证明一个真实算法 Inquiry 能在新架构中完成：

`创建 → 最小 Resource/Locator → 可编辑 Plan → 注册工具 Run → Event/Activity →
Artifact → Finding draft → 审批后导出测试报告`

并能取消、失败、重启和恢复，不损坏数据。

## 2. 实施前用户门

> [!warning] 必须确认
> 开始业务实现前，由用户确认首个真实算法问题。AI 可以推荐，不能替用户决定。

推荐候选：

> 为什么可变长度滑动窗口通常依赖非负输入？引入负数后单调性在哪里失效，
> “和至少为 K 的最短子数组”如何用前缀和与单调队列解决？

它适合作为首切片，因为：

- 当前仓库已有滑动窗口资产；
- 能产生明确 Hypothesis 和最小反例；
- 可比较朴素、错误滑窗和正确单调队列；
- 计算成本低；
- dev 可验证最小代码、测试、Run、Evidence 和 Finding draft；alpha.1 再验证完整
  反例、三种实现、benchmark 和 Decision；
- 不需要先承担 PDF parser 风险。

用户也可选择自己的真实算法问题，但必须有清楚的成功标准。

> [!success] 已确认
> 2026-07-29 用户选择推荐的滑动窗口/负数问题。dev 只运行冻结的现有非负输入
> 单元测试并产出可追溯 Finding draft；反例、单调队列实现、三实现比较、
> property test、benchmark 与最终 Decision 仍全部后置到 alpha.1。

## 12. 每次开发会话的最小闭环

无固定工时时，每次只拿一个 30–120 分钟可完成单元：

1. 从当前 milestone 选择最小失败测试；
2. 写清预期 Artifact/证据；
3. 实现到测试通过；
4. 更新 ADR/contract（若语义变化）；
5. 记录未解决风险；
6. 不顺手加入下一 milestone 功能。

## 13. 开工前最后选择

实现阶段需要用户确认：

1. 使用推荐的滑动窗口/负数问题；
2. 选择另一个真实算法问题；
3. 先只做 runtime，不进入算法内容（不推荐，因为会削弱真实旅程证据）。

这项选择不阻塞本次规划与 Vault 重建；它只阻塞 `v0.3.0-dev` 业务实现。

## 14. 当前实施状态

### 2026-07-29：D0-03 交接模拟后完成

D0-01 的第一次记录只证明了骨架可生成，遗漏了完整授权匹配、全部 locator、
Relation/cardinality 约束、迁移失败回滚和完整证据 manifest，因此不能作为 D0
最终完成证明。D0-02 随后的 D1 交接模拟又发现两个缺口：`staged` Artifact 可缺少
`temp_ref`，以及 `artifact.committed` 可携带空 payload。D0-03 已补齐并重新验证：

- Workstream 0 冻结、legacy schema/UI/reuse 基线与 ADR-001 至 ADR-008 完成；
- 22 个 dev Command、46 个封闭 Event type、17 组状态机、12 个 Relation type、
  6 类可重开 Locator 和结构化错误 envelope 均有机器契约；
- `artifact.staged / committed / reconciled` 具有严格 payload 与可判别
  `ArtifactLifecycleEvent` 联合类型；空 payload、aggregate id 不一致、路径逃逸和
  非法 reconciliation transition 在写入前拒绝；
- `ActionHashMaterial` 覆盖规范化参数、Capability/version/digest、数据级别、
  Provider、读写/网络/进程副作用、网络方法、预算、风险与可逆性；任一变化使旧
  Approval 失效；
- PolicyGrant 精确匹配 Project、Capability、参数 schema、安全级别、Provider、
  目录、网络、预算、并发、次数和期限；未知 schema keyword 失败关闭；
  `decision.confirm / export.publish / object.delete` 不能由 Grant 预授权；
- schema v1 的 24 张 canonical 表由 migration `0001_contract_kernel` 建立；
  dry-run、幂等打开、失败整步回滚、迁移 hash、读取上限和 legacy 隔离均已测试；
- `staged` Artifact 必须携带非空逻辑 `temp_ref`，`available` Artifact 不得保留
  `temp_ref`；SQLite 对三类 Artifact 生命周期 Event 再做失败关闭校验；
- D0→D1 metadata 模拟覆盖 staged/Event/outbox 原子提交、提交前崩溃回滚、重开、
  available 可见性与 10,000 Event cursor replay，2/2 通过；
- 同一 OpenAPI 生成 108 个 schema 与 TypeScript 类型，严格类型检查通过；
- 用户选择的滑动窗口/负数问题、公开 Resource/Locator hash、dev 成功标准和
  alpha.1 scope ceiling 保持冻结，没有偷渡反例、三实现、property、benchmark
  或最终 Decision；
- focused D0 测试 58/58、全量测试 119/119 通过；49 文件证据 manifest 可重算；
- sidecar 仍只有 3 个只读路径并返回 `mutations_enabled=false`，没有把 D0

payload、schema 与 handoff 测试上，以失败测试实现真实 `.partial`/fsync/hash/

SSE；在这些 gate 通过前不建设 React 业务界面。
