# 对标平台与版本演进

## 1. 研究方法

本次没有只看 README 的功能列表，而是检查官方仓库、发布记录、CHANGELOG 和架构
文档，重点问：

1. 首个价值闭环是什么；
2. 后续版本真正花时间修了什么；
3. 哪些结构性问题迫使项目重写；
4. 哪些能力适合 Nana 直接吸收、通过适配器复用或明确拒绝。

版本时间和当前状态以 2026-07-29 可见的官方信息为准。

## 2. 项目对比

## 3. 版本弧线

### 3.1 EAI：先补事实来源和发布纪律

官方仓库：<https://github.com/zGuanZhe/EAI>

可见历史从 2026-07-17 的 0.4 工作区快照开始，随后快速经历 schema bridge、
evidence/projection、取消和 SSE、workspace/service/router 边界、目标与 Run Center、
PDF 预算、查询缓存、Agent/API 隔离与 canonical writes；2026-07-19 到 1.0.0，
2026-07-20 到 1.0.1。

真正值得学的不是两天到 1.0，而是其稳定版门槛：

- SQLite canonical、projection 可重建；
- ContextManifest 与 Evidence Guard；
- preview / confirm / receipt / undo；
- schema ceiling 与只读恢复；
- 安装、卸载、备份和真实数据不变性；
- Agent 能力注册与隔离实验。

对 Nana 的含义：`v0.3.0` 不能只是“新页面能跑”，必须包含数据与发布纪律。

### 3.2 DeepTutor：页面模式最终会统一，安全债会立即追上

官方仓库与发布记录：

- <https://github.com/HKUDS/DeepTutor>
- <https://github.com/HKUDS/DeepTutor/releases>

- [v1.0.0](https://github.com/HKUDS/DeepTutor/releases/tag/v1.0.0)：
  agent-native 主线的稳定起点；
- [v1.4.0-beta](https://github.com/HKUDS/DeepTutor/releases/tag/v1.4.0-beta) 与
  [v1.4.0](https://github.com/HKUDS/DeepTutor/releases/tag/v1.4.0)：把
  Chat/Research/Solve/Question 收敛到统一 agentic engine，并加入多层 Memory；
- [v1.4.1](https://github.com/HKUDS/DeepTutor/releases/tag/v1.4.1)：
  明确记录 shell RCE、路径穿越和跨用户授权等安全修复；
- [v1.5.6](https://github.com/HKUDS/DeepTutor/releases/tag/v1.5.6)：
  本次最终检查快照。

“中间版本持续补知识库、模型路由、恢复与引用可靠性”是对
[完整 release index](https://github.com/HKUDS/DeepTutor/releases) 的综合归纳，
不是对某个未定位 patch 的精确断言。

对 Nana 的含义：不能为“算法/论文/优化”各建一套 Agent；工具权限、路径校验、
取消、恢复、原子写和 Activity 不是后期优化。

官方资料：

- <https://github.com/Future-House/paper-qa>
- <https://github.com/Future-House/paper-qa/releases>

官方 [release index](https://github.com/Future-House/paper-qa/releases) 显示项目从

[v2026.03.18](https://github.com/Future-House/paper-qa/releases/tag/v2026.03.18)。

### 3.7 MLflow、DVC、SwanLab：记录先低侵入，比较后出现

- <https://github.com/mlflow/mlflow>
- <https://github.com/iterative/dvc>
- <https://github.com/SwanHubX/SwanLab>

本节不是逐 patch 的版本断言，而是基于三者官方仓库与本次固定 release 快照的
产品形态比较：共同规律是先低侵入记录参数/指标/环境/产物，再增加筛选、分组、
baseline、并行、恢复、注册和评测。Nana 只定义统一 Run/Artifact 契约和适配器；
成熟平台继续承担其擅长的存储与可视化。

## 4. 跨项目版本规律

1. **先有一个主循环，再有模式与生态**；
2. **分裂的页面运行时最终会被统一**；
3. **生成前可编辑计划能显著降低返工和错误成本**；
4. **真实版本主要消耗在失败恢复、凭据、超时、迁移和打包**；
5. **证据 locator、运行环境和事件日志不能后补**；
6. **自治越高，最小权限、预算、隔离和 Receipt 越重要**；
7. **连续工作区胜过围绕数据库对象的 CRUD 页面**；
8. **能力只能由真实项目事件证明**；
9. **第三方成熟能力应通过适配器复用**；
10. **公开版本速度不能直接外推个人长期项目工期**。

## 5. 吸收、适配、拒绝

### 直接吸收

- Evidence locator、ContextManifest；
- Project / Plan / Run / Event / Approval / Receipt；
- 可编辑 Plan、typed patch、undo/redo；
- append-only 事件、原子写、崩溃后明确状态；
- 双层 Cockpit + Studio；
- schema ceiling、备份恢复、数据不变性门槛。

### 通过适配器

- 模型 Provider、Retriever、PDF parser；
- Git/DVC；
- MLflow/SwanLab；
- Jupyter；
- Obsidian；
- 隔离执行后端。

### 明确拒绝进入首版

- 多用户/团队/社交；
- 大规模技能市场；
- 全套课程/课堂生成；
- 通用 MLOps 平台重写；
- 自动论文发表承诺；
- 为了“看起来聪明”而常态化的多 Agent 长辩论。

## 6. 对 Nana 版本策略的直接结论

版本不能按页面数量命名，必须按可验收旅程：

- dev：统一 Runtime 技术切片；
- alpha.1：算法调查；
- alpha.2：论文/仓库复现；
- beta：工程优化；
- rc：迁移、恢复、安全、安装；
- stable：三模板与所有发布门槛共同通过；
- v0.4：跨项目复用和能力证据；
- v0.5：用户确认后的领域包。
