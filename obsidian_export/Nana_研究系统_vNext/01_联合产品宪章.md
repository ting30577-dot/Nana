> [!important] 当前 D3 权威（2026-08-13）

> `docs/ACTIVE_STATE.json` 为准。
> 本文中与其冲突的旧 gate、重开说明和未勾选项只作为历史快照保留。

## 1. 产品定义

Nana 是一个面向个人长期成长的 Research & Engineering OS。它把一个模糊但真实
的问题转化为：

- 可定位、可核验的证据；
- 明确的假设、反例与决策；
- 可复现的代码、环境、实验和指标；
- 可继续编辑、导出和复用的 Artifact；
- 从真实贡献中派生的 CapabilityEvidence。

不可替代价值不是“再多一个聊天框”，而是把 AI 的研究、编码和实验行为放进同一
项目状态、证据链、权限边界和复现链。

## 2. 核心用户与阶段

主用户是项目所有者本人：

- 正在探索未来科研方向；
- 希望成为某一领域的算法工程师，但不愿过早锁定领域；
- 需要 AI 承担大量资料查找、阅读、编码、实验、整理和比较工作；
- 同时需要理解关键原理、保留判断权，并积累能证明能力的作品；
- 优先使用 Windows，开发投入长期但不固定。

因此 Nana 不是面向大众的多租户 SaaS。首要设计单位是“一个人、多个长期项目、
一个本地工作区”。

## 3. Jobs to Be Done

### J1 推进问题

当我只有一个不完整的问题时，我希望 Nana 自动补充公开证据、提出可检查计划、
执行低风险动作并暴露不确定性，使我能决定下一步，而不是被资料堆淹没。

### J2 验证算法与实现

当我学习或设计算法时，我希望把直觉、边界、反例、实现、测试和复杂度证据留在
同一链路中，使“我看懂了”升级为“我能证明、实现和迁移”。

### J3 复现论文或仓库

当我尝试复现工作时，我希望每个主张能回到论文页码、仓库 commit/symbol、数据
版本和运行环境，并能解释失败来自文献、代码、环境还是资源限制。

### J4 优化工程

当我改善性能或质量时，我希望 Nana 自动保存 baseline、变量、指标、回归和产物，
避免只留下“好像快了”的不可复查结论。

### J5 建立可证明能力

当项目积累后，我希望系统从真实事件中展示自己独立确认、实现、调试、迁移和
决策过的能力，但不以签到、积分或 AI 猜测替代证据。

## 4. 北极星与护栏指标

### 北极星指标

**每月被用户接受、且可由独立复核者重放证据链的 Decision 数。**

一个 Decision 只有同时具备问题、证据 locator、相关 Run、产物、反证/限制和
用户终审，才计入。

### 领先指标

- 从创建 Inquiry 到首个可执行 Plan 的时间；
- 自动执行动作中无需追加人工修复的比例；
- Run 自动捕获代码、环境、输入、参数、指标、产物的完整率；
- Evidence locator 可重新打开成功率；
- 失败 Run 能被分类并从断点恢复的比例；
- 从既有项目复用 Artifact/Method 后节省的重复步骤。

### 不得优化的虚荣指标

- 聊天轮数、生成文字长度、抓取论文数量；
- Agent “思考”时长或工具调用数量；
- 没有证据对应的能力分、等级和学习时长；
- 页面或功能数量。

## 5. 三种 Plan Template 证明同一主循环

| 通用阶段 | Algorithm Investigation | Paper/Repo Reproduction | Engineering Optimization |
|---|---|---|---|
| Goal/Inquiry | 算法为何成立/何时失败 | 哪个论文主张要复现 | 哪个瓶颈要优化 |
| Resource/Evidence | 教材、题解、反例 | PDF、附录、repo、issue | profile、日志、实现、基准 |
| Hypothesis/Plan | 单调性、数据结构、复杂度 | 主张、变量、复现步骤 | 瓶颈假设、实验矩阵 |
| Run | 实现、测试、性质验证 | 环境构建、训练/评测 | baseline、逐项变更、回归 |
| Finding/Decision | 条件、证明、反例 | 复现/部分复现/未复现 | 接受/回退/继续实验 |
| Artifact | 代码、测试、解释 | 锁定环境、结果、复现报告 | benchmark、patch、报告 |

若任何模板需要绕过通用对象、另建隐藏状态或复制 Agent runtime，说明抽象失败，
应先修模型而不是继续加页面。

## 6. 产品原则

1. **Evidence before eloquence**：漂亮叙述不能替代可定位证据；
2. **Plan before spend**：高成本或高风险执行前，计划可编辑、预算可见；
3. **Autonomy with receipts**：自动化越强，行动、权限和结果越可审计；
4. **Artifacts over chat**：聊天用于协作，文件、代码、Run 和 Decision 才是资产；
5. **Failures are first-class**：失败、取消、中断和不确定性必须成为显式状态；
6. **Local-first, not local-only**：本地是事实与控制中心，可按策略使用外部 Provider；
7. **One runtime**：所有模板共享事件、工具、审批、预算和恢复机制；
8. **Real-work growth**：能力成长只能从真实项目证据派生；
9. **Scope before schedule**：无固定工时时，以验收旅程限制范围；
10. **Replaceable adapters**：模型、解析器、检索器、实验平台都可替换。

## 7. 明确不做

`v0.3.0` 不做：

- 多用户、团队权限、社交或排行榜；
- 通用在线课程/课堂生成；
- “一键自动发表论文”；
- 自建完整 Git、DVC、MLflow、SwanLab 或 Jupyter 替代品；
- 290+ 科研技能市场；
- 跨设备云同步；
- 未验证的能力打分 UI；
- 允许 LLM 拼接任意 shell；
- 同时长期维护 PySide6 与新 UI；
- 在用户方向未定前建设某个领域的重型 ontology。

这些边界不是降低目标，而是保证主循环和可靠性先成立。

## 8. 成功与停止条件

### 当前里程碑真相（2026-08-13）

`v0.3.0-dev` 已证明一条受限的 Algorithm Investigation 技术纵向切片：真实浏览器
可完成 `create → provenance → editable Plan → locked T2 Run → Artifact/Finding →
one-time Approval → controlled draft export → Receipt`。这不是 `v0.3.0` stable，也不
等于三个模板、最终 Decision、安装/升级/恢复或通用自治已经完成。

历史 10/10 成功旅程、25/25 浏览器矩阵和 412 项 Python 回归（本段为历史快照，已由
2026-08-13 D3 当前 authority supersede）只证明当时 manifest
固定的受信 fixture、窄 mutation 与固定本地草稿导出边界。它们不能外推证明：

- 通用 Pause/Resume；
- `failed → retry_of` 的用户旅程；
- 任意代码 sandbox 或任意外部发布；
- Local Web 完整生命周期、Tauri 或 stable 发布门。

### `v0.3.0` 成功

- 三个模板各完成一次真实端到端旅程；
- 所有引用、代码、环境、Run 和 Decision 可重放；
- 高自治策略没有越权，失败不会损坏数据；
- Windows 安装、升级、恢复和卸载通过；
- 用户愿意把下一个真实项目放进 Nana，而不是回到手工散落工具。

### 需要重新评估

- 技术切片无法同时满足本地工作区体验和可恢复运行；
- 三模板要求三套本质不同的数据/Agent runtime；
- 每个真实项目都需要大量手工整理才能形成证据；
- Tauri/sidecar 在 Windows 上无法达到可接受的安装和崩溃恢复；
- 用户持续不信任自动动作或无法理解审批/Receipt。
