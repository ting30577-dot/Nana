# 算法核心与未来领域扩展

## 算法为什么仍然重要

算法是重要的大板块，但它不是因为 Nana 必须永远做“刷题软件”，而是因为算法能提供一套跨领域都需要的训练：

- 把问题抽象成可验证的结构。
- 识别不变量、复杂度和边界条件。
- 将文字方法落成伪代码和实现。
- 通过动画、测试和实验发现理解中的漏洞。
- 比较不同方法的取舍。

因此，算法模块是 Nana 统一研究闭环的第一个垂直切片；`v0.2.0-alpha` 先在不依赖 AI 的情况下验证这套结构。

## 与旧算法产品形态的切割

算法仍然重要，不代表旧算法工作台应该被继续包装。下面两种产品形态已经退出路线：

- 手工维护题号、难度、日期、标签、完成数量和连续天数的刷题账本；
- 以模式树、示例代码、播放动画和关联题目为主要使用循环的算法演示页。

它们的问题不是“功能还不够多”，而是要求用户为软件维护记录，或把观看演示误当成掌握方法。以后即使增加自定义输入、更多语言和更多动画，也不能解决这个结构问题。

旧代码并非全部删除。可以下沉复用的只有：

- 与界面无关的算法实现和执行轨迹；
- 绘图画布与播放控制；
- 边界测试和打包链路。

旧页面布局、LeetCode 关联列表、练习 CRUD 与统计不作为新模块骨架。

## 新算法模块：算法研究线程

算法是 Nana 的第一个内容领域，使用与论文、项目相同的研究对象和闭环，而不是拥有一套孤立的刷题数据模型。

```text
真实问题或来源
→ 候选方法
→ 关键假设 / 不变量
→ 最小实现
→ 测试、反例、复杂度与方法比较
→ 有证据的结论
→ 方法卡片与个人判断
```

一条算法研究线程至少包含：

| 对象 | 在算法场景中的含义 |
| --- | --- |
| Research Thread | 围绕一个真实算法问题组织来源、方法、实验和判断 |
| Source | 教材章节、论文、仓库代码或工程问题；题目是 `case` 类型的 Source |
| Claim | 来源明确提出、需要证据支持的结论 |
| Method | 可迁移的算法思想或机制 |
| Evidence | 来源原文、代码位置、测试结果或运行轨迹 |
| Experiment | 最小实现、边界用例、反例或基线比较 |
| Insight | 用户对适用条件、失败原因和迁移价值的判断 |

算法题可以被引用，但只作为类型为 `case` 的 Source。系统不要求用户单独登记“做过这题”；若一次尝试产生了有价值的失败、测试或方法判断，产物自然回到 Research Thread。

“方法卡片”不是独立于 Method 的另一套记录。它是 Method 与关联 Claim、Evidence、Experiment、Insight 的阅读和复用视图。

## 方法实验室的职责

方法实验室是研究线程调用的通用工具，不是旧算法工作台换名。它负责：

- 编辑或载入最小实现；
- 运行正常用例、边界用例与反例；
- 对照不同实现或基线；
- 保存输入、输出、日志和结论；
- 在确有解释价值时，把执行轨迹渲染成可视化；
- 将实验结果作为证据附回当前方法与研究线程。

因此，代码、测试与可视化没有被丢弃，但它们从“页面内容”变成了“验证手段”。

## 面向未来的三层结构

| 层次 | 内容 | 是否现在确定 |
| --- | --- | --- |
| 通用算法基础 | 算法模式、复杂度、证明直觉、实现与实验 | 是 |
| 通用机器学习方法 | 优化、损失、反向传播、正则化、注意力等 | 逐步加入 |
| 研究方向领域包 | CV、NLP、推荐、强化学习、图学习等 | 等方向稳定后 |

研究方向确定后，新增的是领域问题、方法、指标、数据集、论文、代码和实验；底层的来源、证据、方法和洞见对象保持不变。

## 完成标准

一个算法或方法模块只有在用户能够完成下面的闭环时才算真正有价值：

> 看懂问题 → 解释关键机制 → 写出或读懂实现 → 用测试/实验验证 → 说明限制 → 迁移到新问题。
