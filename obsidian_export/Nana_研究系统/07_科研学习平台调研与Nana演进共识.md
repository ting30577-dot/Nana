# 科研学习平台调研与 Nana 演进共识

## 研究问题

> Nana 应该从哪些高质量科研、学习与实验平台中吸收什么，又应该明确拒绝什么，才能长期帮助尚未确定研究方向的个人成长为某一领域的算法工程师？

本文件比较的是产品机制和工程边界，不按 Star 数复制功能。资料以 2026-07-28
可见的项目 README、架构文档和发布记录为准；外部项目随时可能变化。

## 先给结论

Nana 不应成为 EAI、DeepTutor、OpenScience 或 OpenMAIC 的缩小版。它最有价值的
差异仍然是：

> 不是替用户完成研究，也不是替用户上课，而是把“读到的方法”变成“自己能解释、
> 实现、验证、比较和迁移的能力”。

应该形成一个三环相扣的个人科研成长系统：

```text
探索环：问题 → 检索 → 筛选 → 来源工作集
理解环：主张 → 证据 → 多视角质疑 → 用户核对
验证环：方法 → 最小实现 → 实验/反例 → 复现包 → 个人判断
                               ↓
                         可复用方法与能力证据
```

AI 可以规划、检索、解释、质疑和生成候选实现，但不能绕过证据核对、执行授权和
用户判断。Nana 的长期资产不是聊天记录、摘要数量或论文数量，而是经过验证的
`Method + Evidence + Experiment + Insight`。

## Codex × Claude 双模型共识

2026-07-28，Codex 先基于外部项目和 Nana 现有代码形成草案，Claude 再进行两轮
独立反驳与决策收敛。第一轮使用 WawAPI 映射的 Claude Opus，第二轮使用
`claude-fable-5`；中转站曾发生并发限制，失败请求没有计入共识。

双方对重要决策达成以下一致：

1. **北极星不变**：Nana 服务个人研究能力转化，不转向自动科研产出平台。
2. **当前不迁移技术栈**：PySide6 继续承担 Gate A；任何 React/Tauri 迁移都需
   真实阻塞、量化证据和对照垂直切片。
3. **下一阶段只先完成 Gate A**：不先做论文 RAG、GitHub RAG、知识图谱或能力
   图谱 UI。
4. **七个核心对象足够**：不预建通用多对多关系；先用最小溯源链接完成真实
   线程，再依据关系缺口演进。
5. **能力等级是查询结果，不是自评字段**：由用户解释、可运行实现、实验和迁移
   产物派生；Gate C 前不保存分数，不制作等级 UI。
6. **Gate 必须可检查**：机器检查防遗漏和验证产物存在，人工复盘判断内容是否
   真实；不使用字数阈值制造“完成感”。

双方也同意一个反范围膨胀原则：

> 没有真实线程产生的数据，不提前抽象关系；没有 profile 和对照实现，不迁移
> 技术栈；没有可执行产物，不展示能力等级。

`status: staged` 表示：上述原则和执行顺序已经确认，但数据关系细节、Gate B
来源类型、远程资料边界和未来技术栈仍须由真实使用验证。本文中的“建议”属于
待 Gate 触发的候选，不等于已批准开发。

## 代表项目与可吸收机制

### 1. EAI Desktop

- 仓库：[zGuanZhe/EAI](https://github.com/zGuanZhe/EAI)
- 定位：本地优先的个人科研工作台，把询问、证据调查、论文脉络、Canvas 和实验
  Campaign 放进同一条可追踪工作链。
- 关键机制（来自该仓库 README、`docs/PRODUCT.md`、`docs/ARCHITECTURE.md`，
  访问日期 2026-07-28）：
  - `ContextManifest` 记录模型本轮实际看见了什么；
  - `Evidence Guard` 对引用位置和证据充分性 fail closed；
  - Research Task 与普通 Ask 分成独立 lane；
  - 持久修改先生成预览，确认后执行，保留 receipt 和安全撤销；
  - Docker 内执行实验，不能静默回退到宿主机；
  - SQLite 是权威状态，JSON 只是可重放投影；
  - React + Tauri + FastAPI sidecar 形成桌面混合架构。
- Nana 应吸收：
  - 可见的上下文清单、证据资格、引用定位和证据缺口；
  - AI 草稿与用户确认写入分离；
  - 研究任务的暂停、恢复、取消、重试和审计；
  - 实验执行的预览、资源边界、产物 hash 与晋升机制。
- Nana 不应照搬：
  - 当前就引入完整 AI Scientist Campaign、自动写论文和多阶段自治实验；
  - 在首条手动闭环尚未稳定时建设大型 Atlas 和复杂图检索；
  - 让 EAI 的“研究成果生成”目标替代 Nana 的“个人能力转化”目标。

### 2. DeepTutor

- 仓库：[HKUDS/DeepTutor](https://github.com/HKUDS/DeepTutor)
- 定位：终身个性化辅导工作区，将 Chat、Quiz、Research、Visualize、Solve 和
  Mastery Path 统一到 Agent 运行时。
- 关键机制（来自该仓库 README 和发布记录，访问日期 2026-07-28）：
  - 所有模式共享同一运行时和学习上下文；
  - 知识库、书籍、草稿、笔记本、题库、角色和 Memory 跨工作流连接；
  - L1/L2/L3 可检查记忆，并让综合结论回到证据；
  - 多种 RAG 引擎和可插拔文档解析；
  - Guided Learning 使用掌握门槛，而不只输出答案；
  - Python 后端配合 Next.js/React Web 前端。
- Nana 应吸收：
  - 同一研究线程内上下文连续，但每次模型可见范围仍须明确；
  - “理解检查”不能只问用户是否看懂，而应通过解释、预测、实现、反例和迁移任务
    产生证据；
  - 个人记忆可编辑、可追踪、可删除，不把模型摘要当成用户事实；
  - 模型、解析器、检索器和嵌入服务采用能力接口，而非写死供应商。
- Nana 不应照搬：
  - 通用聊天、课程、书库、题库、角色伙伴和即时通讯的全家桶；
  - 以 quiz 数量或聊天陪伴代替真实方法验证；
  - 在个人使用阶段建设多用户、管理员和多渠道通信系统。

### 3. STORM / Co-STORM

- 仓库：[stanford-oval/storm](https://github.com/stanford-oval/storm)
- 定位：通过检索、多视角提问、模拟对话和引用生成长篇知识综述；Co-STORM
  把人加入协作式知识整理。
- Nana 应吸收：
  - 先生成问题地图和视角差异，再检索，不把“搜到什么”当成“应该问什么”；
  - 用 moderator 提出被忽略的问题，用不同角色暴露假设和冲突；
  - 动态概念图用于降低长讨论认知负担；
  - 人可以随时转向讨论，而不是只能等待自动报告完成。
- Nana 不应照搬：
  - 以生成 Wikipedia 风格长文作为完成标准；
  - 用多 Agent 的热闹程度代替证据质量和用户掌握度。

### 4. PaperQA2

- 仓库：[Future-House/paper-qa](https://github.com/Future-House/paper-qa)
- 定位：面向科学文献的高准确率 agentic RAG，支持带引用回答、文献元数据、
  重排、上下文摘要、矛盾检测和本地全文检索。
- Nana 应吸收：
  - 文献身份和版本优先于向量相似度；
  - 检索结果先做相关性筛选和上下文摘要，再进入最终回答；
  - 控制证据数量和多样性，避免把上下文窗口塞满；
  - 证据回答与矛盾检查成为可评测的独立能力。
- Nana 不应照搬：
  - 把本地 PDF 全量索引当作第一里程碑；
  - 把“回答有引用”误认为“用户已核对、理解或能够复现”。

### 5. OpenMAIC

- 仓库：[THU-MAIC/OpenMAIC](https://github.com/THU-MAIC/OpenMAIC)
- 定位：将主题或文档转化为多 Agent 互动课堂，支持幻灯片、测验、白板、3D、
  模拟器、在线编程和项目式学习。
- Nana 应吸收：
  - 可操作模拟优于被动观看动画；
  - AI 应能改变参数、提示观察点，并要求用户预测结果；
  - 交互产物可以导出为独立 HTML，便于复用和分享；
  - 项目式学习用里程碑和产物组织，而不是用连续打卡组织。
- Nana 不应照搬：
  - AI 教师、AI 同学、语音、角色演出和自动课程生成；
  - 把丰富媒体当成科研能力增长的必要条件。

### 6. OpenScience

- 仓库：[synthetic-sciences/openscience](https://github.com/synthetic-sciences/openscience)
- 定位：模型无关的科研工作区，将文献、假设、代码、实验、分析和写作放在一个
  浏览器工作区，并通过技能、MCP、LSP 和科学数据库扩展。
- Nana 应吸收：
  - 文件树、编辑器、终端、实验和研究线程之间使用同一项目上下文；
  - 科学数据库连接器、领域技能和模型供应商均可插拔；
  - 研究产物与 provenance 保存在磁盘，可独立检查和分享；
  - 领域能力通过技能包增加，而不是改写核心。
- Nana 不应照搬：
  - 当前就提供 290+ 技能和全领域自治研究；
  - 让 Agent 拥有默认开放的终端与文件修改权。

### 7. DVC、MLflow 与 SwanLab

- [DVC](https://github.com/iterative/dvc)：数据、模型和流水线版本化，可复现实验；
- [MLflow](https://github.com/mlflow/mlflow)：参数、指标、模型、评测和生命周期；
- [SwanLab](https://github.com/SwanHubX/SwanLab)：训练指标、超参数、硬件、环境、
  Git 状态、媒体和实验对比。

Nana 不应重造成熟的训练平台。应该定义一个轻量 `ExperimentRecord` 和
`ArtifactRef`，可链接 Git commit、DVC hash、MLflow run、SwanLab run 或普通
本地目录；只有小型算法实验由 Nana 内置运行，大型训练委托给专业工具。

## 产品结构：从七个对象到“研究能力账本”

现有七个核心对象保留。下面是长期候选，**Gate A 与 Gate B 均不得实现这些
视图**：

1. **能力查询/导出**：不是新增 `Skill` 实体，而是从用户解释、Method、
   Experiment 和 Insight 派生“我是否已经实现/验证/迁移”的事实。Gate C 前
   只允许 CLI 查询或 Markdown 导出，不做图谱和等级 UI。
2. **研究旅程视图**：按时间展示问题如何经过来源、证据、实验和修正变成判断。
3. **ArtifactRef**：不是研究结论，只是对代码 commit、数据版本、模型、日志、
   图表、MLflow/DVC/SwanLab run 的不可变引用。

能力状态只能由产物派生，不能直接编辑等级：

| 能力等级 | 最低证据 |
| --- | --- |
| 见过 | 保存候选来源和选择理由 |
| 能解释 | 存在标记为用户本人完成的机制、假设和边界说明；AI 草稿不计入 |
| 能实现 | 有最小实现、测试和环境 |
| 能验证 | 有基线、指标、反例或复现结果 |
| 能迁移 | 在新问题中重新使用方法并记录差异 |

这比完成次数、连续天数或 AI 自动评分更接近成为算法工程师所需的真实能力。

## Gate A 前的数据关系裁决

当前实现已经具有以下外键方向；图中的缩进只表示当前直接关系，不表示完整基数：

```text
ResearchThread
├── Source ──< Claim ──< Evidence
└── Method ──< Experiment
           └──< Insight
```

仓储层在创建 Evidence 时已经检查 Evidence 与 Claim 使用同一个 Source。双方
共识是当前不增加通用 `MethodClaimLink` 或 `ExperimentEvidenceLink`：

- Gate A 是少量来源、一个主方法和少量实验，多对多关系尚无真实数据支持；
- 提前建立通用关联会让 UI、迁移和核对流程同时复杂化；
- Method 当前缺少来源溯源是真实缺口。Gate A 实施时增加可空的
  `origin_claim_id`：来源派生的方法必须填写，用户独立提出的方法允许为空。它只
  表示“该方法最初从哪条来源主张提炼”，通过 Claim 间接追到 Source；不表示所有
  支持/反对关系，也不替代具体 Evidence；
- Gate A 复盘必须列出实际遇到的关系缺口，再决定是否需要显式关联表。

## Gate A 的机器检查与人工复盘

建议提供一个轻量 `gate-a-check`，控制在一天工作量以内。它输出报告，不替用户
判断研究质量。

### 机器检查

1. 检查命令显式选择一个 Research Thread；数据库可以存在其他线程。所选线程的
   `question`、排除范围和完成标准非空；
2. 至少两个 Source，版本/定位和选择理由非空。本地定位要求路径存在，网页定位
   要求 URL 语法合法；离线时不把网页暂时不可达直接判为研究失败；
3. 至少一个 Method，机制、假设、适用条件和失败边界非空。来源派生的方法必须
   关联有效的 `origin_claim_id`；`origin_claim_id` 为空即明确表示用户独立提出，
   检查报告需按这两类分别展示，不能把空值静默当作“未知来源”；
4. 至少三条用户标记为“已核对”的 Evidence；本地定位能够重新打开，网页定位
   保存最后一次成功打开时间和当时版本；
5. 最小实现存在；检查器执行项目明确登记的测试命令，并确认正常、边界和反例
   三类命名测试均实际运行且通过；
6. 至少一个 Experiment 保存环境、输入、结果和限制，关联的测试真实通过；
7. 同一个 Method 在不同输入或相邻问题上留下第二次实验，作为迁移证据；
8. 至少一个由用户在确认界面明确确认的 Insight，包含下一步行动；这能区分 AI
   草稿与用户确认，但不是密码学意义上的作者证明；
9. 时间字段可解析为 ISO-8601，枚举值由仓储层拒绝非法输入。

### 人工复盘

- Evidence 是否真的支持 Claim，而不只是“文件存在”；
- 反例是否可能推翻或限制方法；
- 用户能否脱离 AI 解释机制；
- 第二次实验是否是真迁移，而不是复制一份记录；
- Insight 是否包含自己的判断，而不是来源摘要。

机器检查只防遗漏。把废话填进非空字段、复制实验或把 AI 文本标成用户文本仍然
可能骗过程序，因此 Gate A 最终需要一次人工复盘。

## 技术语言决策

### 共识候选

只用 Python 可以完成算法、数据、模型、检索、实验和早期桌面验证，但很难同时
获得高质量复杂交互、浏览器生态、可靠桌面权限边界和未来 Web 复用。正确结论不是
“放弃 Python”，而是“按边界使用多语言”：

| 层 | 推荐语言/技术 | 原因 |
| --- | --- | --- |
| 领域模型、AI、解析、算法、实验 | Python | 科研与 ML 生态最强，现有代码可复用 |
| 稳定本地服务边界 | Python + FastAPI/Pydantic | 让 UI 与研究核心解耦，也方便 CLI/测试 |
| 富交互研究 UI | TypeScript + React | Canvas、编辑器、流式状态、可视化和 Web 复用更成熟 |
| 桌面壳与系统能力 | 后期 Tauri/Rust | 小体积、凭据管理、进程/权限边界；不承载领域逻辑 |
| 实验隔离 | Docker/OCI | 环境可复现，避免模型代码直接污染宿主机 |
| 高性能热点 | 先测量，后选 Rust/C++/CUDA | 没有 profile 证据前不重写 |

### 迁移策略

不立即推倒 PySide6：

1. `v0.2.0-alpha` 用现有 PySide6 完成无 AI 的真实研究线程，证明对象和流程；
2. 同时把 `nana_core` 与 UI 解耦，定义可序列化的 command/query 和
   `ModelProvider`、`DocumentParser`、`ExperimentRunner` 接口；
3. `v0.2.0-beta` 先实现单资料 AI 闭环。若复杂证据阅读、Canvas、流式任务状态
   已明显受 PySide6 限制，再建立 FastAPI sidecar + React 的单个垂直切片；
4. 只有该切片真实优于 PySide6，才将桌面壳迁往 Tauri；禁止“为技术栈现代化”
   进行一次性重写。

### 触发 React/Tauri 垂直切片的量化条件

下面数字是本轮用于防止情绪化重写的**初始工程阈值**，不是经过用户研究证明的
科学标准；Gate A 后可依据真实基线修订。满足任意一类条件，且有 issue、工时或
profile 记录后，才允许做一个对照垂直切片；切片成功不等于立即全量迁移。

1. 连续两个核心 UI 功能在 PySide6 上的实际工时超过预估两倍，且根因明确属于
   框架能力，而非需求反复或设计不清；
2. 核心阅读/核对流程中主线程超过 200ms 的阻塞每分钟至少出现三次，或长文档
   渲染超过 2 秒，并且在 PySide6 内完成一轮优化后仍不达标；
3. 至少三次记录到“必须通过浏览器或其他设备访问研究数据但被桌面端阻塞”的
   真实场景。

若触发，只用同一个证据阅读/核对功能对比 PySide6 与 React 原型的实现工时、
测试、性能和可维护性；没有对照数据，不进入 Tauri 全量迁移。

## 路线图调整建议

### Gate A：真实无 AI 闭环

选择一个与你想成为算法工程师直接相关的问题，围绕一个问题、至少两个来源和
一条主实验链完整留下：

- 问题边界；
- 至少两个来源；
- 一项 Method；
- 一个最小实现；
- 正常用例、边界用例和反例；
- 一条个人 Insight；
- 一次在新输入或相邻问题上的迁移。

Gate A 的最小实现只包括：必要的数据约束、一个轻量检查报告和一条真实线程。
`nana_core` 全面 command/query 平台化、通用插件接口、遥测平台、RAG、知识图谱、
Agent、能力派生查询和新 UI 技术栈都不属于 Gate A。

推荐的第一条真实问题是：

> 为什么可变长度滑动窗口通常依赖非负输入？引入负数后单调性在哪里失效，应该
> 如何用前缀和与单调队列解决“和至少为 K 的最短子数组”？

选择它的理由：

- Nana 已有滑动窗口、前缀和、单调栈/队列相关基础，能复用但不能直接抄答案；
- 可以构造明确反例，验证“方法的适用条件”；
- 同一问题可以比较暴力、普通滑动窗口和前缀和 + 单调队列；
- 能同时产出复杂度分析、测试、可视化轨迹和迁移判断；
- 它是算法工程中常见的“先识别单调性，再选择数据结构”的可迁移方法。

### Gate B：单资料证据闭环

先支持一种来源类型，例如 GitHub 项目：

- 固定仓库 URL、commit 和选择目录；
- AI 生成 Claim/Method/Evidence 草稿；
- Evidence 可以打开到文件与符号位置；
- 用户逐条确认、修正或拒绝；
- 所有写入显示字段 diff，确认后才入库；
- 生成一个最小验证实验并附回 Research Thread。

论文来源随后复用同一闭环，只替换解析器和定位器。

### Gate C：个人能力闭环

- 对一个 Method 进行解释、实现、验证、反例和迁移检查；
- 将失败保留为资产；
- 生成“下一次应该做什么”，而不是生成完成徽章；
- 用固定评测集比较不同模型和提示是否真的减少错误、提高证据命中。

### Gate D：科研工程闭环

- 接入 Git commit 和环境快照；
- 允许引用 DVC/MLflow/SwanLab run；
- 小型实验可本地受控运行；
- 大型训练只生成启动计划和外部运行引用；
- 实验结果必须能回到 Claim、Method 和 Insight。

### Gate E：方向稳定后的领域化

触发条件不是“看了很多论文”，而是：

- 至少连续 8–12 周围绕相近问题形成 Research Thread；
- 出现重复术语、数据集、指标、基线和失败模式；
- 已有方法需要跨来源比较；
- 能写出一组固定评测问题。

“8–12 周”是防止过早定方向的初始观察窗，不是硬性科学阈值；真实课程、项目或
导师要求可以提供更强证据。满足后才建立第一个领域包。领域包包含问题谱系、
方法谱系、术语、数据集、指标、
基线、代表工作、代码、实验模板、失败模式和评测集。

## 明确不进入近期路线的功能

- 通用聊天首页和 AI 角色市场；
- 自动生成完整课程、长报告或论文；
- 批量导入全部 PDF/仓库并自动建知识图谱；
- 多用户、组织、权限后台和即时通讯伙伴；
- 默认开放的自治终端、宿主文件修改和无人监督训练；
- 语音、3D、游戏化和更多动画数量；
- 为了“像成熟产品”而提前重写全部前端。

这些能力不是永远禁止；只有当它们解决经过记录的真实阻塞时才重新评估。

## 需要长期记录的衡量指标

Nana 的成功不能用聊天次数或导入数量衡量。建议记录：

- 从候选来源到深度研究的选择率；
- Evidence 的首次定位正确率和用户核对通过率；
- AI 草稿被用户修改、拒绝的类型；
- 从问题到第一次可运行实验的时间；
- 实验可复现率；
- Method 在新问题中的迁移次数与失败原因；
- 一周后用户能否脱离 AI 解释关键机制；
- Nana 建议的下一步最终有多少被执行并产生证据。

Gate A 当下只记录四项：Evidence 能否重新打开、三类测试是否真实通过、实验能否
在同一环境重跑、从线程建立到第一次可运行实验的时间。其余指标到对应 Gate 再
启用，不先建设遥测体系。

## 当前共识与仍开放问题

### 可立即确认

1. Nana 的北极星是个人研究能力转化，不是自动科研产出。
2. 保留七个核心领域对象，不因竞品增加 Book、Quiz、Course、Agent Persona 等实体。
3. AI 输出先作为草稿，证据核对和持久写入必须由用户确认。
4. 先做单问题、至少两份来源和一条主实验链的纵向闭环，再扩展检索、RAG 和领域包。
5. 多语言按架构边界引入：Python 保留为研究核心，TypeScript/React 和
   Tauri/Rust 由真实 UI 与桌面边界需求触发。
6. 实验元数据可以内置，成熟训练/版本工具通过引用集成，不重复建设。
7. 多模型讨论只用于重要决策、反例和复核，并记录各自观点与最终裁决。
8. Gate A 前不预建多对多关系；Method 的最小来源溯源与 Gate A 检查器一起评估。
9. 能力等级不持久化为分数；Gate C 前只从真实产物派生并导出。

### 仍开放

- Gate A 的首个真实问题最终是否采用下述推荐题；
- Gate B 先做 GitHub 项目还是论文；
- 哪些资料允许发送到远程模型；
- 何时 PySide6 的真实阻塞足以触发 React/Tauri 垂直切片；
- 第一个领域包最终由什么真实研究经历触发。

本轮对第一个问题已给出推荐题目，用户可在真正开始 Gate A 前更换；更换不影响
其余架构共识。

## 接下来只做三件事

1. 一天内固化 Gate A 所需的最小约束和检查报告；为 Method 增加可空的
   `origin_claim_id`，不扩展通用关系图；检查器不负责联网抓取、通用 artifact
   管理或能力评分；
2. 使用现有 PySide6/CLI 完成推荐问题的一条真实研究线程，直到机器检查和人工
   复盘同时通过；
3. 写一页 Gate A 复盘，记录真实暴露的数据关系、交互和实验复现缺口，再决定
   Gate B 先做 GitHub 项目还是论文。
