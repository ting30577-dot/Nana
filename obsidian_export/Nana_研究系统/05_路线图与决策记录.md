# 路线图与决策记录

路线图按能力成熟度划分，不按未来某个研究方向的假设排期。当前处于 `v0.2.0-alpha`，新研究骨架已经成立并进入早期验证。

`v0.1.0` 只作为冻结的历史原型保留。旧 `v0.2` 方案没有形成正式发布版，其功能定义已经取消；由于仓库已有 `v0.1.0` 历史标签，当前 `v0.2.0-alpha` 属于重新定义后的研究闭环版本线，不继承旧功能表。

## 版本划定

版本号按能力边界划分，不按旧功能表排期。当前已经进入 alpha；`alpha`、`beta`、`rc` 都属于重新定义后的 `v0.2.0` 研究闭环验证线。

| 版本 | 状态 | 边界 |
| --- | --- | --- |
| `v0.2.0-dev` | 已结束的迁移态 | 遗留代码可以暂存；不发布，也不把旧页面列为新产品能力。 |
| `v0.2.0-alpha` | 当前：新骨架成立 | 刷题账本与旧算法工作台退出运行入口；Research Thread、Source、Claim、Evidence、Method、Experiment、Insight、遗留数据安全归档与方法实验室骨架成立；一个真实算法问题可以完成无 AI 的最小研究验证。 |
| `v0.2.0-beta` | 首条 AI 闭环可用 | 单篇论文或单个项目可以完成选择性导入、AI 中性精读、证据定位与用户核对、用户修正、最小实现/实验和方法卡片。 |
| `v0.2.0-rc` | 冻结候选版 | 不再加入新对象，只处理闭环完整性、数据可靠性、隐私边界、打包和交互问题。 |
| `v0.2.0` | 首个稳定研究版 | 第一条单资料研究闭环可以被反复使用，产物可追溯、可修改、可再次进入实验。 |
| `v0.3.0` | 方法复用版 | 支持跨来源比较相近方法，并让已有方法卡与实验在新问题中被复用；与旧路线的“论文库 v0.3”无关。 |

领域包、Research Lens、模型专业化和 Web 不预先绑定版本号，等触发条件满足后再排入后续版本。刷题账本永久退出后续正式路线；批量全文知识库、模型训练/微调、多人协作平台、自治研究 Agent 或更多动画数量也不作为当前里程碑。

## 决策状态边界

| 状态 | 内容 | 含义 |
| --- | --- | --- |
| 已确认 | 桌面端优先、算法为首个领域、单资料精读、证据与用户修正分层 | 当前设计和开发必须遵守 |
| 永久退役 | 学生学习工作台、手工刷题账本、旧算法演示页、旧固定版本路线 | 不以改名、隐藏或“以后可能有用”为理由恢复 |
| 延后判断 | Research Lens、领域包、多模型路由、模型训练/微调、Web | 不是拒绝；`v0.2.x` 不做，只有真实需求与触发条件出现后才定版本 |
| 仍然开放 | 首个模型供应商、资料上传边界、AI 可靠性评测和自动动作权限 | 不在文档中假装已经解决 |

“延后判断”与“永久退役”不能混用。旧代码可以暂存于 `v0.2.0-dev`，但不会因此改变其产品决策状态。

## 当前阶段：切断旧形态并建立研究骨架

目标不是堆功能，而是证明一次从问题到方法沉淀的过程能在 Nana 中完成。

- 从运行入口移除手工刷题账本和旧算法工作台。
- 在移除前检测已有本地刷题记录，并提供一次性导出或迁移，禁止静默丢失用户数据。
- 建立 Research Thread、Source、Claim、Evidence、Method、Experiment、Insight 的最小对象。
- 把算法执行、测试与可视化下沉为方法实验室工具。
- 采用桌面端优先，保持核心逻辑与界面分离。

完成标志：选取一个真实算法问题，在不调用 AI 的情况下完成“问题 → 方法 → 实现 → 测试/反例 → 个人判断”。

### 遗留刷题数据退出标准

退役旧入口不能以丢失数据为代价。`v0.2.0-alpha` 至少满足：

1. 检测 `%LOCALAPPDATA%\Nana\nana.db` 中的旧记录数量，并在操作前告知用户。
2. 生成带 `schema_version`、导出时间和全部原字段的无损 JSON 归档；导出记录数必须与数据库一致，并能被程序重新读取校验。
3. 默认只归档，不把所有做题记录自动伪装成研究成果。用户可以选择把有价值的记录迁移为 `case` 类型 Source，并指定新建或已有的 Research Thread。
4. 迁移时保留原题号、标题、难度、日期、状态和笔记为 legacy metadata，但这些字段不再驱动统计或连续打卡。
5. 任一导出、校验或迁移步骤失败时，不移除旧入口、不改写旧表；原数据库保留为只读回退来源，直到用户明确确认。

## 下一阶段：接入 AI 并验证单资料精读

- 建立统一的模型接入配置。
- 支持针对单篇论文或单个项目的选择性导入，并固定论文版本或仓库 commit。
- 完成中性整理、论文页码/章节或项目文件/符号级证据定位、用户核对和结构化精读。
- 让代码、测试、可视化和实验结果可以回到同一个 Research Thread。
- 保存用户对 AI 输出的修改和判断。

暂不做：

- 训练专用模型。
- 绑定某个研究方向。
- 批量导入所有论文全文。
- 为了表现“智能”而增加的自主执行。
- 与能力转化闭环无关的完整科研基础设施。

## 中期阶段：形成可复用的方法库

- 论文、项目和算法共用来源与方法对象。
- 将精读结果沉淀为方法卡片、主张和证据。
- 支持相近方法的比较与迁移。
- `v0.2.0` 稳定后才允许评估 Research Lens；它不依赖领域包，也不自动成为 `v0.3.0` 验收项。
- 用固定问题集评估不同模型和提示方案。

## 后期阶段：方向稳定后的领域化

当研究方向由真实课程、项目、导师和阅读经历逐渐确定后，再加入对应领域包：

- 问题与任务分类。
- 方法谱系。
- 数据集、指标和基线。
- 代表性论文与代码。
- 可复现实验。
- 领域特有的失败模式。
- 与其他领域的关联。

此时 Nana 仍然是一个开放的研究系统，不应退化成只服务单一领域的知识库。

## 版本与平台决策

| 议题 | 决策 | 原因 |
| --- | --- | --- |
| 当前开发线 | `v0.2.0-alpha` | 新研究骨架成立，进入早期验证 |
| 旧版本处理 | 保留历史标签和可复用代码，不沿用旧路线 | 历史可追溯，但不让旧方案继续限制新设计 |
| 平台顺序 | 桌面端优先，Web 后置 | 当前是个人、本地、研究资料和实验场景 |
| Web 触发条件 | 出现跨设备、同步或协作的真实需求 | 避免为不确定用户提前建设服务端 |

## 已确认的决策

| 议题 | 决策 | 原因 |
| --- | --- | --- |
| 最终定位 | 将外部研究成果转化为自身能力的个人研究成长系统 | 更符合长期目标，而非当前学生身份 |
| 是否拆出独立论文项目 | 先不拆，作为 Nana 的核心模块 | 论文阅读、算法实现和实验验证最终属于同一闭环 |
| 论文导入方式 | 候选池广泛收集，全文选择性导入 | 控制噪声、成本和“伪理解” |
| 核心对象 | 方法/算法，论文作为来源 | 方法才是可迁移、可复用的资产 |
| AI 专业化时机 | 前期不训练，先做可替换框架 | 研究方向和数据都尚未稳定 |
| 专家观点的使用 | 从公开材料整理为 Research Lens，并保留来源与边界 | 不把公开表达冒充真实思想、当前意见或模型权重 |
| 算法模块地位 | 保留为重要领域，但重建产品结构 | 它使用统一研究线程与方法实验室，不继承刷题账本和动画工作台 |
| 外部设计的吸收 | 学习后按 Nana 的目标重新组织 | 采百家之长不等于功能对齐 |
| 科研平台调研后的北极星 | 保持个人研究能力转化，不转向自动科研产出 | Codex 与 Claude 独立评审后达成一致 |
| 近期技术栈 | Gate A 继续使用 Python/PySide6 | React/Tauri 迁移必须由量化阻塞和对照切片触发 |
| 能力等级 | 从用户解释、实现、实验与迁移产物派生，不保存分数 | 避免自评和 AI 评分制造伪进步 |
| Gate A 关系模型 | 保留七对象和当前最小关系，真实使用后再扩展 | 没有真实多对多数据时不预建关系图 |

## 功能取舍准则

面对一个新功能，优先判断：

1. 它能否帮助用户理解、实现、验证或迁移一种方法？
2. 即使没有任何同类项目作为参照，它对 Nana 是否仍然有价值？
3. 它是在强化现有闭环，还是只让产品看起来更完整？
4. 如果来自其他项目，是否已经被重新消化为 Nana 自己的工作方式？

## 仍然开放的问题

- 最终研究方向是什么，以及哪些方向应成为第一批领域包。
- 首批支持哪些模型供应商，是否需要本地模型。
- 论文全文、代码和研究记录哪些可以发送到外部 API。
- AI 输出的可靠性如何评测，什么标准才算“真的帮上忙”。
- 哪些动作必须由用户确认，哪些动作可以自动完成。
- 什么时候积累了足够数据，值得做微调或本地化。

这些问题现在不需要被假装解决。它们应该在使用 Nana 的过程中由真实需求和失败案例推动。

## 当前最近的一步

当前先完成 `v0.2.0-alpha` 的准入工作：

1. 检测并导出/迁移已有刷题数据，再让刷题账本和旧算法工作台退出运行入口。
2. 建立 Research Thread、Source、Claim、Evidence、Method、Experiment、Insight 的最小骨架。
3. 选一个真实算法问题，在不依赖 AI 的情况下完成“问题 → 方法 → 实现 → 测试/反例 → 个人判断”。

推荐首题：

> 为什么可变长度滑动窗口通常依赖非负输入？引入负数后如何用前缀和与单调队列
> 解决“和至少为 K 的最短子数组”？

详细竞品证据、Gate A 检查条件和多语言架构触发条件见
[[07_科研学习平台调研与Nana演进共识]]。

这条骨架成立后，再进入 `v0.2.0-beta`：

> 选定论文或项目 → AI 中性精读 → 证据核对 → 最小实现/实验 → 个人判断 → 方法卡片。
