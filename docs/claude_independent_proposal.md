# Claude 独立提案：可追溯复现驱动的自治科研工程系统

> 形成时间：2026-07-29  
> 模型：Claude Opus 4.8（经用户配置的兼容渠道）  
> 输入：仅使用 `rebuild_evidence_pack.md`，生成时未看到 Codex 的本轮方案。  
> 状态：独立提案，不代表共同结论。

## 结论

### 主循环

- **方案**：Nana 的一句话定义是“一个把论文/问题转化为可追溯复现结论的自治
  科研工程系统”。第一价值闭环是可追溯的论文复现循环：给定一篇论文或一个具体
  问题 → AI 阅读并抽取带定位的主张/方法 → 生成可编辑的复现计划 → 在沙箱中
  运行代码与实验（不可变 Run）→ 产出链接回原始证据与运行记录的结论笔记。
  项目执行是唯一主循环；个人能力成长是从工作证据（事件、Run、审批）派生出来
  的只读视图，不建独立积分/等级系统。
- **反对方案**：以文献综述/知识策展为首个闭环。它对“成长为算法工程师”的
  贡献弱，且不强制产生可运行工件。
- **失败条件**：若样本论文普遍不可复现，复现循环会退化为无产出；需先做可行性
  抽样。

### 双层 UI

- **方案**：第一层研究驾驶舱展示项目状态、待审批、最近 Agent 活动和能力证据；
  第二层项目内科研 IDE 包含文件树、PDF 定位阅读、代码编辑器、终端、实验/Run、
  Agent 日志和会话，并共用统一 Agent 运行时。
- **默认工作流**：打开项目 → 查看待审批/计划 → 批准 → 观察 Agent 执行 →
  审核最终产物。
- **反对方案**：继续当前 CRUD 式六按钮录入。
- **失败条件**：两层上下文断裂，驾驶舱无法反映 IDE 内的真实进展。

### 技术栈

- **方案**：不立即整体替换，但立即冻结 PySide6 新功能。先把领域、Agent、RAG
  和实验能力下沉为独立 Python 服务（FastAPI + HTTP/SSE），使用 Python 服务
  加最小 Vite/React 前端验证首个纵向切片；切片通过后正式以 Tauri + React/TS
  + Python sidecar 替换 PySide6。
- **反对方案**：长期使用 PySide6 + QWebEngineView 嵌入编辑器/PDF。
- **失败条件**：单人同时换栈和建立主循环，被 Windows 打包、首启与 sidecar
  可靠性拖垮。因此 Python 核心必须可通过 API/CLI 独立测试，UI 不阻塞主循环。

### 领域、事件和工件模型

最小实体：

- Project；
- Source：保留原始文件、解析版本和 locator；
- Claim/Method：强制携带 source locator，禁止伪造引用；
- Plan：typed、可编辑；
- Run：不可变，保存代码版本、环境、输入、指标和 artifact；
- Artifact；
- Event：append-only Agent 行为日志；
- Approval/Receipt：preview/confirm/receipt/undo；
- Output：回链笔记。

存储使用 canonical SQLite + 可重建 projection；实验对接 MLflow/DVC，而不是
重写完整 MLOps。

- **反对方案**：先做简单表结构、可追溯性以后再补。
- **失败条件**：Event/Run 不具备 append-only 与不可变约束，将无法审计与复现。

### 高自治与审批

- **默认自主**：读取/解析已授权文件、检索、起草计划与代码、只读分析、写入
  scratch 区。
- **必须审批**：执行消耗算力或写沙箱外的实验、联网写、付费调用、安装依赖、
  修改环境、删除/覆盖用户数据、shell 命令、提交最终产物到 Obsidian/canonical、
  访问凭据。
- 使用能力注册表、运行预算、可中断性和审计日志。
- **反对方案**：无审批的全自动。
- **失败条件**：过密审批使自治失效；过粗审批导致安全事故。

### 隐私分级

- `public`：公开论文，可上云；
- `private`：私人笔记，默认本地或经批准；
- `confidential`：未公开代码，默认不上云，优先本地模型或脱敏；
- `secret`：凭据，永不进入 LLM 或日志，存 OS keychain。

Agent 每次云调用前声明上下文数据级别，策略引擎决定放行、询问或阻断。

- **反对方案**：统一经中转站云模型。
- **失败条件**：没有满足 confidential 任务的本地模型时，这类任务无法自治。

### 版本路线

- `v0.3.0`：首个纵向切片。单项目、导入一篇 PDF、解析与 locator、抽取主张/
  方法、可编辑复现计划、审批、沙箱运行不可变 Run、产出回链笔记、Windows
  端到端 happy path；
- `v0.4.x`：可靠性，覆盖首启、打包、超时、取消、恢复、原子写、迁移和凭据；
- `v0.5.x`：统一运行时，扩展 source/retriever/实验类型；
- `v0.6.x`：能力证据视图和跨项目复用；
- UI 换栈版本只在切片验证后进入，并包含安装/卸载、备份恢复和真实数据不变性。

- **反对方案**：先做酷炫功能广度。
- **失败条件**：把 IDE 全组件塞进 `v0.3.0`，导致切片无法交付。

### 迁移

- 先备份废版 Obsidian；
- 当前 SQLite 只归档，不把旧 CRUD 数据和 UI 当作新架构；
- Source/Claim/Method 等概念只作为设计输入；
- 旧刷题 DB、算法演示代码和 CRUD UI 只读归档，必要时作为示例 Source/Artifact；
- 新 Nana 连接 Obsidian 作为知识来源，不重造笔记库。

### 验收

- 主张可以跳转源定位，伪造引用为零；
- 计划执行前可编辑；
- 同代码、环境和输入得到可复现、可比较的 Run；
- 未审批的高风险动作全部拦截；
- 最终笔记回链有效；
- confidential 内容上云会被阻断；
- 指标包括端到端成功率、locator 准确率、Run 复现率、首结果耗时和审批漏放率；
- 保持 61 项基线，并增加数据契约、append-only、Evidence Guard、沙箱和迁移
  幂等测试；
- 若抽样论文复现成功率过低，主循环转为“文献综合 + 部分实现”。

## 决策依据摘要

- **事实**：Nana 只有四次提交且未经历真实迭代；61 项测试通过；当前没有 PDF
  导入、证据定位、编辑器、终端、实验运行时、Agent 日志和审批撤销；UI 是
  CRUD；旧 Vault 是废版并已获准备份后替换。
- **推论**：当前 SQLite 数据不值得主导新架构；Web 前端更适合 IDE 需求。
- **假设**：样本论文中存在足量可复现对象；存在可用于 confidential 的本地模型。
- **建议**：以复现循环为主循环、核心 Python 化、可追溯性进入首版、先做切片
  再换栈。

## 支持与反对证据

- OpenScience 支持“目标 → 文献 → 假设 → 代码 → 实验 → 写作”的连续工作区；
- 用户未来算法工程师目标支持复现作为工程训练；
- PaperQA2 的解析和恢复版本史说明复现工程门槛很高；
- EAI 和 OpenScience 支持 Web 工作区；
- 单人无固定工时和大量可靠性版本反对立即完成式换栈；
- 项目版本共同模式支持能力成长来自真实工作证据。

## 对可能替代方案的预置反驳

1. 反对立即整体换 Tauri 并同步建设全部主循环；
2. 反对先做文献综述闭环；
3. 反对长期保留 PySide6；
4. 反对投入大量精力迁移旧 CRUD 数据和 UI；
5. 反对为了折中而长期双栈并行维护。

## 收敛条件

1. 对 3–5 篇不同子领域论文做可复现性抽样；
2. 先冻结 locator、append-only Event、不可变 Run 和审批收据等数据契约；
3. Python 核心 + FastAPI/SSE，UI 可插拔；
4. `v0.3.0` 只做单论文端到端 happy path；
5. 零伪造引用、零越权执行进入 CI；
6. 先归档再替换 Vault 和旧仓库。

## Claude 标记的未决事项

1. 首个主循环是复现还是综述，需要可行性抽样；
2. Tauri、Qt+WebEngine 或纯 Web，需要最小原型比较；
3. confidential 数据是否有可用本地模型，证据不足；
4. 内置沙箱还是依赖 Docker，需要 Windows 方案证据；
5. 能力证据的派生规则延后至主循环稳定。
